# Bytecode patches

The mod's own coremod, `com.exiledradio.trailsandtalesbackport.asm.TrailsAndTalesCore` (sorting index 1001, so every
class arrives with SRG member names in a real instance and MCP names in dev; each patch matches both). One transformer
per patch, no MixinBooter, nothing loaded from inside a transformer. A target of another shape than expected (another
coremod got there first and changed it) is left alone and logged, so vanilla's behavior stays. Inserted code changes no
stack-map frame: no new local, and a parameter is read only on a method's first line (Mojang's unpatched classes keep
ProGuard's frames, which drop a parameter once vanilla stops reading it).

Each patch's hook checks its own config and `Presentation.isAtLeast(...)`, so with the feature off the game behaves as
1.12.2 does. `Asm.APPLIED` lists the patches the running game applied (the self-tests read it).

## Release-jar check

The dev runs recompile Minecraft with javac, so they never see Mojang's ProGuard stack-map frames, which drop a local once
vanilla stops reading it. Before a release, boot the release jar on a plain Forge 14.23.5.2847 dedicated server:

    ./gradlew build
    tools/release/boot-server.sh <server dir> build/boot.log <BackportCore jar> build/libs/TrailsAndTalesBackport-<version>.jar

The script empties the server's `mods/`, puts in the jars named, deletes the world and boots with
`-Dtrailsandtalesbackport.loadPatched=true`. `PatchCheck` then loads and verifies every class P1 to P20 patch (24 on a
server, 26 on a client) and logs `PATCHCHECK ok N` or `PATCHCHECK FAIL <class>`. With other family mods, add their
`-D<modid>.loadPatched=true` through `JVM_ARGS`; the script then wants one `PATCHCHECK ok` line per mod. A patch with a
new target class adds it to `PatchCheck`.
